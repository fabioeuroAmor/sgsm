# T15 — GET válido com Accept: application/xml

## Comando executado

```
curl -s -i -X GET "http://localhost:8080/v1/api/servicos-medicos/241760a1-efdc-44c6-b3c2-1f3a64013fe4" \
  -H "Authorization: Bearer eyJhbGciOiJIUzUxMiJ9...[REDIGIDO]" \
  -H "Accept: application/xml"
```

## Resposta crua

```
HTTP/1.1 406
Accept: application/json, application/*+json, application/yaml
X-Content-Type-Options: nosniff
X-XSS-Protection: 0
Cache-Control: no-cache, no-store, max-age=0, must-revalidate
Pragma: no-cache
Expires: 0
X-Frame-Options: DENY
Content-Type: application/problem+json
Transfer-Encoding: chunked
Date: Sat, 15 Aug 2026 15:18:18 GMT

{"detail":"Acceptable representations: [application/json, application/*+json, application/yaml].","instance":"/v1/api/servicos-medicos/241760a1-efdc-44c6-b3c2-1f3a64013fe4","status":406,"title":"Not Acceptable"}
```

## Avaliação

- Status real observado: **`406 Not Acceptable`** — a app NÃO ignora o `Accept:
  application/xml` e devolve JSON; em vez disso, o Spring MVC (content negotiation
  padrão) recusa a requisição porque não há um `HttpMessageConverter` para XML
  registrado, retornando 406 com a lista de representações aceitáveis
  (`application/json, application/*+json, application/yaml`) no corpo e no header
  `Accept` da resposta.

**RESULTADO: APROVADO** (comportamento correto e seguro de content negotiation; documentado como achado — cliente que envie apenas `Accept: application/xml` recebe erro, não fallback silencioso)
