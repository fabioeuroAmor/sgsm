# T12 — GET com id truncado (UUID com um caractere a menos)

## Comando executado

```
curl -s -i -X GET "http://localhost:8080/v1/api/servicos-medicos/241760a1-efdc-44c6-b3c2-1f3a64013fe" \
  -H "Authorization: Bearer eyJhbGciOiJIUzUxMiJ9...[REDIGIDO]" \
  -H "Accept: application/json"
```

(id enviado tem 35 caracteres — o `241760a1-efdc-44c6-b3c2-1f3a64013fe4` original sem o
último `4`.)

## Resposta crua

```
HTTP/1.1 404
X-Content-Type-Options: nosniff
X-XSS-Protection: 0
Cache-Control: no-cache, no-store, max-age=0, must-revalidate
Pragma: no-cache
Expires: 0
X-Frame-Options: DENY
Content-Type: application/problem+json
Transfer-Encoding: chunked
Date: Sat, 15 Aug 2026 15:17:19 GMT

{"detail":"Serviço médico não encontrado: 241760a1-efdc-44c6-b3c2-01f3a64013fe","instance":"/v1/api/servicos-medicos/241760a1-efdc-44c6-b3c2-1f3a64013fe","status":404,"title":"Recurso não encontrado","type":"https://sgsm.com.br/erros/recurso-nao-encontrado"}
```

## Avaliação

- Status real observado: **`404`**, via o handler customizado `RecursoNaoEncontradoException`
  (`type: https://sgsm.com.br/erros/recurso-nao-encontrado`) — NÃO caiu em 500. `UUID.fromString`
  do Java é permissivo quanto ao tamanho de cada grupo separado por `-` (não exige
  estritamente 8-4-4-4-12 caracteres), então o id truncado com 35 caracteres foi
  interpretado como um UUID sintaticamente válido — porém **diferente** do original: o
  `detail` mostra `241760a1-efdc-44c6-b3c2-01f3a64013fe` (note o `0` inserido antes de
  `1f3a64013fe`), resultado do parsing leniente por posição de bits, não uma cópia
  literal da string truncada. Por ser um UUID "válido" mas inexistente na tabela, retorna
  404 pelo fluxo normal de "não encontrado", igual a T02.

**RESULTADO: APROVADO** (sem crash/500; comportamento de parsing do UUID documentado como achado interessante, não como bug)
